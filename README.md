# 示例科室排班系统 v2

> **脱敏说明（GitHub 版）**：本仓库为脱敏公开版——人员姓名已替换为 AAA–KKK、海关号/工号已替换为 111–999、单位名已替换为「示例科室」，数据库文件未包含在内（首次启动自动建库并写入上述示例人员）。功能代码与内部版一致（v6.31）。


科室职能轮休排班：11 名人员按月在线自助选休，保存草稿后正式提交；管理员调取全员提交的源数据生成最终表，一键补满、人工调整、保存并提交发布。成员提交的源数据带时间戳保留一年。

## 运行（Mac / Linux 通用）

```bash
cd duty-roster
./run.sh
```

`run.sh` 首次运行会自动创建虚拟环境 `.venv` 并安装依赖（需要联网），之后一条命令启动。打开：

**http://localhost:3000**

手动方式（等价）：

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/uvicorn backend.main:app --port 3000
```

云服务器（云服务器）上以 systemd 服务 `duty-roster` 运行，开机自启、崩溃自动重启：

```bash
sudo systemctl status duty-roster   # 状态
sudo systemctl restart duty-roster  # 重启
sudo journalctl -u duty-roster -f   # 看日志
```

依赖：FastAPI + uvicorn（服务）、openpyxl（Excel 导出）、ortools（自动补满求解；装不上时自动切换内置最大流算法兜底）。

数据库为单个 SQLite 文件 `backend/duty.db`，首次启动自动建库并写入种子人员（全新数据库，无测试数据）。备份只需拷这个文件。

## 界面结构（左侧目录 + 分块）

- **主页**：本月月历总览（最终表优先，否则提交源数据汇总）+ 每日在岗统计（三行：全员/干部/协管员）。v2.2 起不再有「已选情况」卡片面板——每人的提交状态直接由姓名颜色标注：绿 = 已提交、橙 = 已保存未提交、黑 = 未提交（成员合并页同理）。
- **我的选班**：在整月月历上点自己一行的格子选假期符号，改动先在本地暂存（橙色描边），点「保存」写入草稿；确认后点「提交」——提交即生成带时间戳的源数据快照并锁定本人编辑（管理员退回后可改并重提，重提产生新版本，旧版本保留）。
- **排班表**：只读全表 + 导出 Excel / 生成图片（导出内容与展示口径一致，最终表优先并会在导出响应头标注来源）。
- **管理 · 规则设置**：新建月度计划（月份、应休 Q、自选上限 S、先行组）、修改当前计划设置与阶段覆盖、每日在岗硬约束说明。
- **管理 · 数据处理**：最终表工作台——「调取数据」用全员最新提交快照重建最终表（未提交者为空行）；「一键补满」不限是否有人已选，从最终表现有计数把所有人（含科长）补到 Q；可直接点格手工修改最终表；「保存」落时间戳；「提交发布」锁定并让全员在主页看到最终表；成员提交情况表可逐人「退回」。
- **管理 · 人员设置 / 权限设置 / 历史数据**：人员增改；账号角色/启停/重置密码；近 12 个月计划与全部提交版本记录查询。
- **修改密码**：所有人可用。

## 规则与实现对应

**月度计划**：管理员按月新建，设置应休天数 Q（如 2026 年 11 月 Q=9）和自选上限 S（默认 6）。

**自选额度**：科长自选至多 Q 天；其余干部与协管员至多 S 天。补满后所有人最终恰好休满 Q 天。

**选休窗口**（排班月的上一个月，服务端日期自动判定；管理员可用阶段覆盖手动开放）：

| 阶段 | 日期 | 开放对象 |
|---|---|---|
| 1 | 上月 24 日起 | 科长 |
| 2 | 上月 25 日起 | 当月先行组（A/B，含该组协管员） |
| 3 | 上月 26 日起 | 另一组（含该组协管员，全部开放） |

- 先行组按排班月轮换：奇数月 A 组先（如 11 月），偶数月 B 组先，管理员可覆盖。
- 协管员随所在组开放：JJJ属 A 组、KKK属 B 组，与同组干部同一天开放（v2.2 起取代旧的“协管员按月轮流优先”规则）。

**每日硬约束**（服务端每次保存都校验，普通成员无法突破；管理员改最终表超限时保存但给出警告）：

- 9 名干部每日休假 ≤ 4 人 ⇒ 干部在岗 ≥ 5 人；
- 其中科领导（3 人）每日休假 ≤ 2 人 ⇒ 科领导在岗 ≥ 1 人；
- 协管员在岗 ≥ 1 人/天：2 名协管员每日最多休 1 人（v2.2 新增硬约束，成员选班/一键补满均强制；另一名协管员已休的日期，在协管员本人行上变灰、服务端拒绝）。
- 达到上限的日期界面变灰（协管员不受干部名额限制，但受上一条协管员上限约束）。

**假期符号**：轮休 ✓、补休 R、排正限制 Z、备勤 B、年休假 O、公差 *、病假 △、借调 J、探亲假（单身）Φ、探亲假（四年）☆、夫妻分居 #、加正 ●、丧假 D、婚假 E、法定假 F、看护假 N、产假 S、保健假 W。除“备勤 B”外均计为休假（计入个人额度与每日上限）；空白格 = 正常上班。

**一键补满**：OR-Tools CP-SAT 约束求解（不可用时最大流兜底）：保持已有格子不变，把每人补到 Q 天轮休 ✓，硬保证每日干部在岗 ≥ 5、科领导在岗 ≥ 1、协管员在岗 ≥ 1（v2.2）；软目标为每人每周（自然周）尽量 ≤ 2 天、补休向较空日期分散。无解时返回明确错误（协管员约束卡死时会明确指出），不写半成品。

**源数据保留**：提交快照存入 `submissions` 表，带提交时间、永不覆盖、不自动删除；「历史数据」可查近 12 个月计划与全部版本，满足一年留存要求。

**导出**：Excel 与现行表格同版式——标题“示例科室排班表（X月可休Q天）”、日期+星期表头、科领导/干部/协管员分组、符号、右侧每人合计、底部每日在岗/干部在岗/协管员在岗三行（v2.2 新增协管员行，<1 标红）、图例脚注、周末列底色。图片由前端把整月表渲染为 PNG 下载（html2canvas CDN，无网络时不可用并有提示）。

## 后续迁移微信小程序说明

API 先行设计不变：全部功能都在 `/api/*` JSON 接口上（登录、草稿、提交、调取、补满、发布、导出、账号管理），网页前端只是消费端之一。微信小程序阶段后端可原样部署（届时 SQLite 可平滑换 MySQL/PostgreSQL），小程序端按同一套接口重写界面即可。
